===============================================================================
1. EXECUTIVE SUMMARY
===============================================================================

BlackMarket AI is a broad local-first market research and paper-trading product.
The source contains a Tauri desktop client, supervised FastAPI/Python engine,
shared React dashboard, Next.js private-preview frontend, Binance public-data
clients, strategy research/backtesting, simulated Spot/Futures order lifecycle,
risk and learning modules, SQLite persistence/recovery, assistant, notifications,
and a terminal interface.

The project has substantial implementation and automated coverage. The most
important release blockers are:

1. A Telegram token was present in .env.example. It has been removed from the
   template, but revocation and external history/artifact review remain open.
   A local scan found no Telegram-token-shaped value in this workspace.
2. The adaptive risk engine no longer reports fabricated drawdown or
   correlation values. These measures are unavailable unless the caller
   supplies persisted high-water-mark evidence and validated aligned returns.
3. This workspace has an initialized Git repository with no commits. All files
   are uncommitted. Prior branch, commit and CI claims in old documentation
   cannot be verified against this source tree.
4. No current Tauri installer, clean Windows install/upgrade/uninstall, hosted
   backend, production exchange stream, release signature, or backup restore
   was verified in this audit.
5. The website has a shared-password gate and shared backend state. It is not a
   multi-user service with individual identity or account/data isolation.

Configuration now fails closed for unsupported real-trading mode, malformed
explicit boolean/numeric values, and non-SQLite database URLs. Unused Binance
private API key/secret settings were removed. The exposed Telegram values were
removed from .env.example, and the template now disables Telegram by default.

The score is an engineering-readiness score, not a financial or profitability
rating. No market strategy, backtest, model or trading result was evaluated for
profitability.

Remaining work:

3.2 Backend API and desktop security boundary

Implementation evidence:
- src_tauri/backend/main.py binds to loopback by default and rejects non-loopback
  peers unless remote API mode is explicitly enabled.
- REST API requests use bearer authentication; token comparison uses
  hmac.compare_digest.
- The desktop WebSocket separately checks the loopback peer and requires a
  token-authentication message.
- CORS uses a fixed Tauri origin list plus explicitly configured remote origins;
  development origins are added only in desktop development mode.
- /health is public for startup readiness and returns readiness/version fields,
  not credentials or private account data.
- The desktop supervisor generates per-process API and shutdown tokens, keeps
  them out of frontend source/URLs/logs, checks readiness, and requests graceful
  shutdown from its owned child.
- REST and WebSocket rate limits are process-local.

Remaining work:
- Re-test REST and WebSocket auth independently on the exact release build.
- Development WebSocket origins were removed from the packaged CSP and placed
  in blackmarket-desktop/src-tauri/tauri.dev.conf.json. Configuration tests
  pass; verify the effective CSP in the exact release artifact.
- Process-local rate limits reset on restart and do not coordinate across
  instances; hosted multi-instance protection requires shared/upstream controls.
- Review the explicit public community/share routes separately from authenticated
  API routes in release acceptance.

3.3 Market data and exchange connections

Implementation:
- exchange/spot_client.py and futures_client.py use public Binance REST market
  endpoints; no order endpoint or signed order request was found in the reviewed
  exchange clients/routes.
- Scanner discovery, ticker snapshots, candle history, multi-timeframe refresh,
  and staleness/freshness checks are present. A WebSocket manager and stream
  reconnection helpers exist as components.

Remaining work:
- Production scanning uses public REST polling; exchange stream subscriptions
  are not configured in the production scanner. Binance streams are not
  established as configured/operational in production.
- Do not describe the feed as live until both markets' stream status, freshness,
  reconnect and REST fallback have been tested against the release deployment.
- The three live exchange tests were deliberately deselected from the local run.
- Check rate-limit handling, exchange schema changes, clock skew and incomplete
  candles against live fixtures before release.

3.4 Strategies, research and backtesting

Implementation:
- Strategy families, signal evaluation, Strategy Lab, historical backtesting,
  report persistence and strategy comparison are present.
- Historical tests cover strategy behavior, timeframe handling and walk-forward
  validation.

Remaining work:
- No fresh backtest or performance result was produced for this audit.
- Verify assumptions for fees, spread, slippage, funding, candle availability,
  partial fills and liquidation in every strategy-report path.
- Display provenance, sample interval, data gaps, fees and limitations with
  every persisted/public strategy report. Never describe backtests as guarantees.

3.5 Paper trading and risk

Implementation:
- Paper simulator models order/position lifecycle and supports simulated costs,
  leverage, funding and liquidation logic.
- Database repository saves completed trade history and closes its position in
  one SQLAlchemy session/transaction (database/repositories.py:289-334).
- Partial trade and remaining position are also persisted in one transaction
  (database/repositories.py:336-358).
- The paper-trading risk manager and autonomous paper readiness gates are
  separate from the adaptive risk assessment module.

Resolved in this remediation:
- risk/adaptive_risk.py no longer returns fixed drawdown or correlation
  placeholders. Drawdown requires a persisted high-water mark and tracking
  start time. Correlation uses validated, chronological, aligned UTC return
  series with a minimum observation count and positive-correlation clustering.
- Missing risk evidence produces UNAVAILABLE rather than a safe-looking score.
  Focused tests cover missing inputs, invalid high-water data, aligned returns,
  ordering, and persistence continuity across engine recreation.
- Integration limitation: the main simulator does not supply all persisted
  high-water/return evidence to the adaptive assessment. Treat those factors as
  unavailable unless a caller provides the required data. This adaptive
  assessment is not the simulator's independent trade gate.

3.6 Learning and model lifecycle

Implementation:
- Prediction outcome records, dataset building, training, chronological/
  walk-forward validation, confidence calibration, model registry, promotion
  checks, rollback and performance views exist.
- The test suite includes leakage/alignment, validation, promotion and rollback
  cases.

Remaining work:
- No new model was trained, promoted, or evaluated in this audit.
- The legacy LearningOrchestrator now forwards validation evidence to model
  promotion; live-service status reports blocked promotion rather than claiming
  activation when promotion fails. Regression tests cover both paths.
- Run a reproducible training/evaluation from a clean database and record the
  dataset version, time interval, sample counts, temporal split, metrics,
  calibration and rollback result.
- Verify model artifact provenance, migration compatibility and failed-training
  recovery on a disposable copy.
- Validation metrics do not establish profitability or future predictive power.

3.7 SQLite, backups, recovery and events

Implementation:
- SQLite uses WAL, foreign keys, busy timeout, full synchronous mode, startup
  quick/integrity checks and migration logic.
- Trade close persistence is transactional and position recovery uses persistent
  identifiers; recovery idempotence is covered by tests.
- Backup, restore, integrity checking, event persistence and startup recovery
  routines are present.

Remaining work:
- Thirty compressed database backups were found under data/backups/. The root
  .gitignore already excludes data/backups/*.db.gz. Their contents were not
  opened and their tracked status cannot be known without Git commits.
- Validate backup creation and restore, sidecar handling, corrupt database
  recovery and retention on disposable files.
- The application does not encrypt databases, model artifacts or backups.
  Document OS-level encryption and filesystem protection.
- Non-SQLite DATABASE_URL values are rejected during startup validation. The
  database migration/backup code remains SQLite-specific.

3.8 Assistant and external integrations

- Optional Telegram notification code validates configuration and the template

Remaining work:

3.9 Website private preview

Implementation:
- Next.js server-side single-password gate uses a signed session cookie and
  scrypt password verification.
- Proxy checks a session, applies request limits/body bounds and sends backend
  credentials from server-side environment only.
- Eight session/rate-limit tests pass.

P1 conditional blocker for public hosting:
- There is no multi-user identity, roles, per-user portfolio/position/history/
  settings/workspace isolation, or account-level authorization.
- The shared backend is common state for all logged-in preview users. The
  X-BM-Community-Owner header is not a substitute for verified user identity.
- Session revocation and login/proxy/API rate limits are process-local.

Required fix:
- Keep the website private. Before public multi-user access, add a real identity
  provider, server-verified principals, tenant-scoped database access and
  authorization, shared durable session/revocation and rate-limit controls,
  security review, privacy/retention operations, and deployment E2E tests.
- blackmarket-web/package-lock.json is now present; CI uses npm ci and the local
  locked dependency audit reported zero vulnerabilities. Commit the lockfile
  with the release source and repeat the audit there.
- Verify HTTPS ingress, durable storage, SSE/auth behavior, startup, restart,
  backup and restore on the actual hosted service.

3.10 Configuration and distribution

Resolved in this audit:

Remaining work:

4. FINDINGS BY SEVERITY
===============================================================================

P0 — EXPOSED TELEGRAM TOKEN (LOCAL TEMPLATE FIXED; REVOCATION OPEN)

Evidence:
- A non-placeholder Telegram bot token and chat ID were in .env.example when
  the audit began. The token value is intentionally not repeated here.
- .env.example now has empty Telegram values and TELEGRAM_ENABLED=false.

Impact:
- Anyone with access to the exposed token may act as the bot and access its
  authorized chat interactions. Treat the token as compromised.

Required fix:
- Revoke the token via BotFather immediately.
- Search any public repository history, release archives, logs and screenshots.
- If published, remove the value from history where feasible after revocation;
  never rely on history rewriting instead of token revocation.
- Configure a new token only in private runtime configuration and verify logs
  do not include it.

P1 — ADAPTIVE RISK EVIDENCE AND SIMULATOR INTEGRATION

Status: PLACEHOLDER CALCULATIONS RESOLVED; EVIDENCE INTEGRATION REMAINS OPEN.

Evidence: risk/adaptive_risk.py calculates drawdown only when persisted
high-water-mark evidence is supplied and calculates correlation from validated
aligned UTC return series. Insufficient evidence is represented as unavailable.
Focused risk tests pass.

Impact: the main simulator does not currently supply all evidence to the
adaptive assessment. These fields can remain unavailable and must not be
presented as measured. The adaptive assessment is not the independent simulator
trade gate.

Remaining action: integrate durable high-water/return evidence where this
assessment is displayed or retain the unavailable state.

P1 — NO SOURCE PROVENANCE OR CURRENT-HEAD RELEASE EVIDENCE

Evidence:
- git status lists all project files as untracked.
- git log has no commits; HEAD cannot be resolved.
- Existing documentation referred to differing source commits and CI runs; those
claims cannot be tied to the current source.

Impact: a release cannot be mapped to a reviewed source revision or reproducible
CI evidence.

Required fix: establish the intended remote/branch, commit reviewed source,
inspect the resulting diff/history for secrets/data, run CI on that commit, and
build/verify the exact artifact from that same commit.

P1 — HOSTED WEBSITE IS NOT A MULTI-USER SERVICE

Evidence: blackmarket-web/README.md: Authentication limitations and current

caller-supplied community owner header.

Impact: shared-password login does not identify individual users or isolate
account state. One user's data/actions cannot be treated as isolated from
another user's.

Required fix: retain private-preview classification. Implement authenticated
user identity, authorization and tenant-scoped data access before public
multi-user hosting. Add hosted E2E tests for cross-user read/write denial.

P1 — EXCHANGE STREAM AND WATCHDOG RECOVERY ARE NOT PRODUCTION-VERIFIED

Evidence:
- The production scanner currently uses public REST polling; exchange stream
  subscriptions are not configured in the production scanner.
- The watchdog stall handler logs a stall but does not restart components.

Impact: real-time feed continuity and automatic self-healing are not established.
Users could confuse local API/WebSocket readiness with live Binance stream
readiness.

Required fix: test production Spot/Futures stream availability, feed age, stream
failure/reconnect, REST fallback and frontend degraded state. Either implement
and test recovery or document that watchdog detection only logs and does not
recover.

P1 — WINDOWS RELEASE ARTIFACT ACCEPTANCE NOT VERIFIED

Evidence: release scripts/workflows are present; this audit did not build the
Tauri/NSIS installer or perform clean-machine install/upgrade/uninstall.

Impact: packaging, native startup/shutdown, data retention and artifact identity
remain unproven for this source tree.

Required fix: run the installer workflow on a committed source revision; verify
clean install, readiness, local auth, duplicate launch, graceful close, upgrade,
preserved user data, uninstall cleanup, signature status, manifest and SHA-256.
